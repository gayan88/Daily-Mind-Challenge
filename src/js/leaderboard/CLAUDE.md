# src/js/leaderboard

## Files

- **`leaderboard-data.js`** — `getOverallLeaderboard(period, limitCount)` (sums a period's `gameScores` per user across every game in `GAMES`) and `getGameLeaderboard(game, period, limitCount)` (single-game ranking for that period, `game` being `'wordle' | 'sudoku' | 'wordsearch'`). `period` is one of `'today' | 'week' | 'month' | 'year' | 'all'` — `'today'` and `'all'` are exact-date-equality and no-filter respectively, `'week'/'month'/'year'` are **rolling** windows (last 7/30/365 days including today, via `getDateDaysAgo()` in `src/js/utils/helpers.js`), not calendar-aligned periods — simpler and avoids timezone/calendar-boundary edge cases (these are unrelated to Championships' *calendar-aligned* days/weeks/months, see below). Both functions filter out banned users via a `getBannedUids()` query that's cached in-memory for the page's lifetime (so switching tabs on the leaderboard page doesn't re-fetch the banned list every time). Both are now thin wrappers around a shared `aggregateScores(snap, bannedUids)` helper. `findUserInLeaderboard(rows, uid)` is a plain array helper, no Firestore call. `getGameScoresForDateRange(game, startDate, endDate)` reuses that same `aggregateScores()` helper for an explicit `[startDate, endDate]` range instead of a named rolling period -- used by `progression/championship-service.js` to determine a *closed calendar* day/week/month's winner; unranked/unlimited, since its callers there just want the top entry. `getOverallScoresForDateRange(startDate, endDate)` is the same idea with no `gameType` filter at all -- the "Overall" counterpart, used only by `admin-page.js`'s marketing Top 10 viewer (see `admin/CLAUDE.md`) to pull a combined-games ranking for an arbitrary past day/week/month, not just the named rolling periods the two functions above support.
  - `getGameLeaderboard()` queries `where('gameType', 'in', GAME_TYPES[game])`, not a single `==` match against `game` itself -- each game writes multiple distinct `gameType` values depending on mode (e.g. Word Search alone is `wordsearch`/`wordsearch-classic`/`wordsearch-tournament`/`wordsearch-tournament-bonus`). An earlier version of this function filtered on the literal `game` string directly, which meant only that game's Daily Challenge scores ever showed up on its own leaderboard tab -- Classic and Tournament points were silently invisible there (though still correctly counted on "Overall", which has no `gameType` filter at all). `GAME_TYPES` here is now derived from `src/js/progression/game-registry.js#GAMES` (the single source of truth for each game's full gameType list, added as part of the progression-engine work) rather than a locally hardcoded object; `wordle-challenge-creator` (the reward a Challenge creator earns per solver, not a play) is deliberately included in Wordle's list, so a player's Wordle-tab total stays consistent with the Wordle portion of their Overall-tab total rather than mysteriously falling short of it. Firestore treats an `in` query the same as `==` for composite-index purposes (it's executed as the union of one equality query per value), so this didn't need a new index -- the existing `(gameType ASC, scoreDate ASC)` composite still covers it.
  - Period filters query `scoreDate`, **not** `gameDate`. `gameDate` doubles as a deterministic `gameScores` doc-ID key for Tournament/Classic/Challenge a Friend modes (a tournament id, a random token, a challenge id, etc.) and is only ever a real calendar date for Daily Challenge docs -- so filtering by `gameDate == today` silently excluded every Tournament/Classic/Challenge score from Today/Week/Month/Year leaderboards (they only ever showed up under "All-time", which has no date filter at all). `scoreDate` is a second field, set to the real play date on every `gameScores` doc regardless of gameType (see each game's `*-data.js`), that exists purely for this filtering -- `gameDate` itself is untouched and still serves its original doc-ID-key role. This fix only applies going forward: scores written before it don't have `scoreDate` and remain invisible outside "All-time" (no backfill was done).
  - `getXpForUids(uids)` — batched `registeredUsers.xp` lookup (`documentId() in [...]`, chunked by 10, same pattern as `progression/championship-service.js#fetchExistingPeriodIds()`), used to show each leaderboard row's real sub-rank avatar without a doc-per-row read. Callers must only pass uids for rows actually being rendered (a page of `leaderboard-page.js`'s pagination, or `home.js`'s top-5 preview) -- never every aggregated row up to `FETCH_CAP` -- so the cost stays bounded to what's on screen. A uid with no doc (or a doc missing `xp`) is simply absent from the returned `Map`, treated as 0 XP by callers. `getRegisteredUserSummary(uid)` is the single-player counterpart (`xp`/`currentStreak`/`loginPoints` off one plain `getDoc`, no batching needed since it's only ever one specific clicked player at a time) -- used by `player-profile-modal.js` below.
- **`leaderboard-page.js`** — page glue for `src/html/leaderboard.html` (uses `trySession()`, not `initShell()`, so the page is public: an anonymous visitor or crawler sees the real leaderboard with `uid` null, calling `showLoggedOutHeader()`; every `uid` use already resolves safely to "no matching row"): two independent tab rows (game type: Overall/Wordle/Sudoku/Word Search; period: Today/Week/Month/Year/All-time), tracked as two pieces of state that both feed the same render call. The period tab is labeled "All-time" in the UI rather than "Overall" specifically to avoid confusion with the game-type tab of the same name — they mean different things (all games vs. all time). Rows are paginated for display, `config/leaderboardPageSize.size` at a time via "Load More" — but since `getOverallLeaderboard()`/`getGameLeaderboard()` already have to aggregate every matching `gameScores` doc for the period before they can rank anyone (there's no way to correctly determine "top N" without seeing every user's total first), the full ranked array (up to a soft `FETCH_CAP` of 500 rows) is fetched once per tab/period change and kept in memory; "Load More" just reveals more of it client-side, with **no additional Firestore reads**. Championship finalization is **no longer** triggered from this page (or by any visitor at all) -- it moved to an admin-only manual action (`admin-page.js`'s "Championships" section, see `admin/CLAUDE.md`) specifically because the old "any registered visitor's page load" trigger let whichever visitor's local device clock crossed into a new period first decide the cutoff for literally everyone, with no way to know if a slower/behind timezone still had legitimate plays coming. `render()` also calls `renderYourRank()` (Phase 10) with `findUserInLeaderboard(allRows, uid)` -- a small always-visible "You're ranked #N" summary above the tabs, independent of how far the visitor has scrolled/"Load More"'d, since finding your own highlighted `.hlb-you` row previously required clicking through pages if you weren't near the top. Shown for guests too (guests appear on leaderboards, Section 4 of the progression spec) -- not gated to registered players. No extra Firestore read: it's a pure lookup against the same `allRows` array `renderVisible()` already has, so it inherits that array's `FETCH_CAP` truncation (a player ranked below 500 shows as "haven't scored yet," same pre-existing limit `.hlb-you` always had).

  Each row now also shows that player's sub-rank avatar (`.hlb-avatar`, resolved lazily via an `avatarCache` Map + `ensureAvatars()`, which only fetches XP for rows in the *currently visible* slice via `getXpForUids()` above, not the whole fetched array -- the cache persists across tab switches and "Load More" clicks since XP doesn't change moment-to-moment) and is clickable (`.hlb-row-clickable`, mouse + keyboard, one delegated listener on the row container), opening `player-profile-modal.js#showPlayerProfileModal()` for that player.
- **`player-profile-modal.js`** — the "click a leaderboard row" player profile popup, shared by this page's rows and `home.js`'s top-5 leaderboard preview (both render the same `hlb-row` shape). Builds its own DOM into `document.body` on first use (same pattern as `games/wordle/wordle-summary-modal.js`), reusing the generic `.modal-overlay`/`.modal-dialog` component from `components.css`. Shows the player's avatar, name, rank label, a "#N Global Rank" pill, a 4-stat row (Total Points, Total XP, Global Rank, Day Streak), an Overall Level/XP progress card, and a grid of their **earned** achievement badges only (not the full In Progress/Not Started breakdown -- that needs assembling the clicked player's entire progression context, far more reads than a quick-look popup on a stranger warrants), each badge showing its label underneath, capped to one visible row (`max-height` + its own `overflow-y: auto`, `overflow-x: hidden`) regardless of how many achievements the player has, so the popup's overall height stays predictable instead of growing with the achievement count. The header background is set inline per-open to that player's `rank-service.js#MAIN_RANKS` tier color (a per-rank "trading card" look); guests get a fixed neutral slate color instead (no `MAIN_RANKS` tier applies to them) and skip the stats/level/achievements sections entirely (same registered-only gate as everywhere else). "Global Rank" is the one genuinely expensive field -- ranking a player against *every* player's all-time total means the same unbounded `getOverallLeaderboard('all', 500)` scan `home.js`'s own "Overall Rank" tile already accepts once per home visit; repeating that per row click would be wasteful, so the fetched all-time array is cached at module scope after the first click (`getAllTimeRowsCached()`) and reused for every subsequent click during the page's lifetime, with its own `.catch()` isolating a failure there from breaking the rest of the popup.

## Firestore indexes

Every period/game combination is covered by indexes. Equality-only queries (`scoreDate == today`, `gameType == X`) use Firestore's automatic single-field indexes; range queries (`scoreDate >= startDate`) also use the automatic single-field index; and the equality+range combination (`gameType == X AND scoreDate >= startDate`, used by `getGameLeaderboard()`'s week/month/year periods) is covered by the `(gameType ASC, scoreDate ASC)` composite index in `firebase/firestore.indexes.json`, since Firestore composite indexes support an equality prefix plus one trailing range field. The older `(gameType ASC, gameDate ASC)` composite is still present but no longer used by any query now that period filtering moved to `scoreDate` -- left in place rather than removed, since an unused index is harmless.

## Why the daily login bonus isn't included

Per the intended points-system design, the daily login bonus is deliberately **excluded** from these leaderboard totals — the leaderboard is meant to rank game-playing skill/effort, not who happened to log in. (The player's own "today's points" stat on the home page's status card *does* include the login bonus, computed separately in `src/js/pages/home.js` — that's a different, personal-facing number from the competitive leaderboard.)

## Known limitation

The "All-time" period sums every `gameScores` document ever written per user with no `limit` on the underlying read — fine at current scale, but unbounded as the collection grows. The Load More pagination in `leaderboard-page.js` doesn't help with this: it only paginates *display* of the already-fully-aggregated result, not the read itself (see above) — `FETCH_CAP` bounds how many ranked *rows* come back, not how many raw docs get read to compute them. A pre-computed/cached leaderboard collection (updated by a scheduled Cloud Function) would be the way to make this scale further; out of scope for now, consistent with this project having no Cloud Functions at all.
