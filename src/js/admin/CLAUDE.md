# src/js/admin

Everything here is gated on `profile.isAdmin` — `admin-page.js` redirects non-admins away immediately. `src/html/admin.html` is the only page that loads this folder's code.

## Files

- **`activity-summary-data.js`** — `getDailyActivitySummary(dateString)`: a single `where('scoreDate', '==', dateString)` equality query against `gameScores` (cheap and safe at any scale, since it's always bounded to one day's docs, unlike an all-time sum), then a client-side tally over that one result set -- unique logged-in users deduped by `userId` (guest vs. registered), and a per-mode breakdown grouped by game with per-game subtotals via a hardcoded `ACTIVITY_ROWS` map. That map is also where Tournament mode's subtlety is handled: Tournament writes multiple `gameScores` docs per run (one per puzzle/word, plus a one-shot completion doc), so only the one-shot completion `gameType` (`wordle-tournament`, `sudoku-tournament-bonus`, `wordsearch-tournament-bonus`) is counted as "one completion" -- counting every tournament-prefixed gameType would overcount by however many puzzles/words each tournament has. `wordle-challenge-creator` (the creator's per-solver reward) is excluded entirely, since it's a reward doc, not a play, and would double-count activity already represented by `wordle-challenge`.
- **`moderation.js`** — direct Firestore operations restricted to admins by security rules: `lookupUserByUsername()`, `setUserBanned()`/`setUserAdmin()` (toggle a `registeredUsers` doc's moderation fields).
- **`wordle-admin.js`** — Firestore layer for Wordle admin features. Daily Challenge word pool: `listDailyWords()`, `addDailyWord(word, startDate)` (append-only — each word doc's own id IS the "YYYY-MM-DD" date it plays on, not a numeric id. The very first word (empty pool) requires `startDate`, the admin's chosen launch date, becoming Challenge #1; every word after that ignores `startDate` and is automatically dated one day after the previous word's date (`_meta.lastDate + 1`, via `addDaysToDateString()`), so admins never compute dates by hand and adding more words later never touches an already-seeded date. Bumps `_meta.{totalCount, firstDate, lastDate}`, which `src/js/games/wordle/wordle-daily-data.js#getTodayChallenge()` reads. Rejects a word (case-insensitive) already anywhere in the pool -- one extra `listDailyWords()` read up front), `bulkAddDailyWords(rawWords, startDate)` (CSV-import version of the above -- same date-assignment rule applied to a whole list at once, written via `writeBatch()` chunked at `BATCH_LIMIT - 1` (499) words per batch so a mid-import failure can never leave `_meta.lastDate` pointing past a word that didn't actually land; `_meta` is only written once, in the final chunk. Rejects the whole import, before any write, if a word repeats within the file or already exists in the pool), `updateDailyWord(currentDate, { word, date })` (corrects a word's text and/or date -- changing the date deletes the old doc and writes a new one under the new date, since Firestore doc ids can't be renamed in place; refuses to overwrite another word already on the target date). Calls the private `renumberDailyWords()` afterward, which re-derives every word's `challengeNumber` from date order and rewrites `_meta` from scratch -- this is also how a malformed/legacy entry (e.g. one seeded before this date-keyed scheme existed, missing a real date or a `challengeNumber`) gets repaired: just edit it with the date it should actually have, and renumbering fixes the rest. Deliberately no delete for individual daily words -- removing one from the middle of the calendar would leave a permanent gap on that date, since new words only ever get appended after `_meta.lastDate`, never backfilled; a bad entry gets corrected via `updateDailyWord()` instead. Tournaments: `listTournaments()`, `createTournament({ name, words, timePerWordSeconds, bonusPoints })` (active by default), `setTournamentActive(id, active)` (deactivate without deleting history), `deleteTournament(id)`.
- **`sudoku-admin.js`** — Firestore layer for Sudoku admin features. Daily pool is date-keyed, mirroring `wordle-admin.js`'s scheme exactly (see that file's doc comments for the full rationale): `listDailySudokuPuzzles()`, `addDailySudokuPuzzle(puzzle, solution, startDate)` (each puzzle doc's own id IS the "YYYY-MM-DD" date it plays on; the very first puzzle requires `startDate`, becoming Challenge #1, every one after that is auto-dated `_meta.lastDate + 1`. Rejects an exact-duplicate puzzle string already in the pool), `bulkAddDailySudokuPuzzles(rawPairs, startDate)` (CSV-import version, same date-assignment rule applied to a whole `{puzzle, solution}[]` list at once via chunked `writeBatch()`. Rejects the whole import, before any write, if a puzzle string repeats within the file or already exists in the pool), `updateDailySudokuPuzzle(currentDate, { puzzle, solution, date })` (can also move a puzzle to a different date -- deletes the old doc, writes a new one, since Firestore doc ids can't be renamed; this is also the repair path for a malformed/legacy entry). Both of the latter two call the private `renumberDailySudokuPuzzles()` afterward to re-derive every puzzle's `challengeNumber` from date order and rewrite `_meta` from scratch. Deliberately no delete for individual daily puzzles, same reasoning as Wordle's Daily Words. Classic pool (still numeric-id/random-pick, no date concept): same three functions plus a `difficulty` ('easy'/'medium'/'hard') argument, sharing one numeric id counter across all three difficulties, plus `bulkAddClassicSudokuPuzzles(rawEntries)` (CSV-import version of `addClassicSudokuPuzzle()`, same chunked-`writeBatch()` shape as the Daily bulk functions). Both `addClassicSudokuPuzzle()` and the bulk version reject a puzzle string that's already somewhere in that *same difficulty's* pool (a duplicate across two different difficulties is fine, since each difficulty's pool is picked from independently) -- the admin table groups puzzles by difficulty for the same reason (`groupByDifficulty()`, shared with Word Search's Classic table, always rendered Easy/Medium/Hard regardless of id-interleaved insertion order, each difficulty its own always-open `.admin-subsection` since there are only ever three). Tournaments: `listSudokuTournaments()`, `createSudokuTournament({ name, puzzles, completionBonus })` (active by default; `puzzles` is an array of `{ puzzle, solution }` pairs; `completionBonus` is set per tournament, unlike the time limit/max errors which stay global via `config/sudokuTournamentSettings`), `setSudokuTournamentActive()`, `deleteSudokuTournament()`. `validateSudokuPuzzlePair(puzzle, solution)` runs before every puzzle write (Daily, Classic, and each puzzle in a Tournament create) — checks both strings are 81 characters, the solution is a valid completed grid (every row/column/3x3 box has each digit 1-9 exactly once), and the puzzle's given cells match the solution — since there's no way to hand-verify an 81-character string visually.
- **`wordsearch-admin.js`** — Firestore layer for Word Search admin features. Daily pool is date-keyed, mirroring `wordle-admin.js`'s scheme exactly (see that file's doc comments for the full rationale): `listDailyWordsearchPuzzles()`, `addDailyWordsearchPuzzle({ theme, words }, startDate)` (each puzzle doc's own id IS the "YYYY-MM-DD" date it plays on; the very first puzzle requires `startDate`, becoming Challenge #1, every one after that is auto-dated `_meta.lastDate + 1`. Rejects a puzzle whose word set already matches one in the pool -- see `wordSetSignature()`, a sorted/uppercased join so word order and theme don't affect the comparison), `bulkAddDailyWordsearchPuzzles(rawEntries, startDate)` (CSV-import version, same date-assignment rule applied to a whole `{theme, words}[]` list at once via chunked `writeBatch()`. Rejects the whole import, before any write, if a word set repeats within the file or already exists in the pool), `updateDailyWordsearchPuzzle(currentDate, { theme, words, date })` (can also move a puzzle to a different date -- deletes the old doc, writes a new one, since Firestore doc ids can't be renamed; this is also the repair path for a malformed/legacy entry). Both of the latter two call the private `renumberDailyWordsearchPuzzles()` afterward to re-derive every puzzle's `challengeNumber` from date order and rewrite `_meta` from scratch. Deliberately no delete for individual daily puzzles, same reasoning as Wordle's Daily Words. Classic pool (still numeric-id/random-pick, no date concept): same three functions plus a `difficulty` argument, sharing one numeric id counter across all three difficulties, plus `bulkAddClassicWordsearchPuzzles(rawEntries)` (CSV-import version of `addClassicWordsearchPuzzle()`, same chunked-`writeBatch()` shape as the Daily bulk functions). Both `addClassicWordsearchPuzzle()` and the bulk version reject a word set (`wordSetSignature()`) that's already somewhere in that *same difficulty's* pool, same reasoning and same `groupByDifficulty()`-grouped admin table as Sudoku's Classic pool. Tournaments: `listWordsearchTournaments()`, `createWordsearchTournament({ name, puzzles, completionBonus })` (`puzzles` is an array of `{ words }` entries; `completionBonus` is set per tournament, unlike puzzle count/time limit/completed-and-failed-puzzle points, which stay global via `config/wordsearchTournamentSettings`), `setWordsearchTournamentActive()`, `deleteWordsearchTournament()`. `validateWordList(words, { minCount, maxCount })` runs before every word-list write — checks the count matches the mode's requirement (`src/js/games/wordsearch/wordsearch-modes.js` is the single source of truth for these numbers), every word is alphabetic and 4-9 letters, and **no word is a substring of another word in the same list** (case-insensitive, either direction) — this last check is a genuine correctness requirement, not a nicety: the engine's selection matching checks both the forward and reversed letter string against every remaining word, so a substring pair like "CAT"/"CATFISH" would make one drag ambiguously satisfy two words.
- **`admin-table-grouping.js`** — pure, game-agnostic grouping/labeling helpers shared by every game's admin Daily/Classic tables: `monthLabel()`, `groupWordsByMonth()` + `groupMonthsByYear()` (Daily puzzles/words nested year → month, both collapsed by default), `groupByDifficulty()` + `DIFFICULTY_LABELS` (Classic pools split into Easy/Medium/Hard sections, each open by default), and `wireCollapsibleToggles(container)` (click-to-toggle wiring for a freshly-rendered batch of `[data-collapsible]` subsections, scoped to one container rather than the page-wide `wireCollapsibleSections()` since these are regenerated on every render). Extracted out of `admin-page.js` (which still defines and uses them for Wordle/Sudoku/Word Search, just via an import now) specifically so `connections-admin-page.js` could reuse the exact same grouping instead of drifting into its own copy — Connections' Daily/Classic tables originally shipped as flat, ungrouped lists and had to be retrofitted to match; **any future game's admin module should import from here from the start**, not add its own grouping later.
- **`connections-admin.js`** / **`connections-admin-page.js`** — Connections' admin, kept in two self-contained modules so `admin-page.js` only needed one import and one `initConnectionsAdmin()` call. `connections-admin.js` is the Firestore layer: `parsePuzzleText()` (blocks separated by a blank line, each 4 lines of `Group name: w, w, w, w` ordered easiest→hardest, with an optional leading `difficulty: easy|medium|hard` line), `validatePuzzle()` (4 groups × 4 words, all 16 unique case-insensitively, ≤14 chars), Daily (`addDailyConnectionsPuzzles()` -- date-keyed like Sudoku's, first puzzle needs a start date, add-only; `updateDailyConnectionsPuzzle()` edits content in place, date/number never move), Classic (`addClassicConnectionsPuzzles()`, one shared numeric id counter, duplicates rejected per difficulty by an order-independent word signature), and Tournaments (`createConnectionsTournament({ name, puzzles, timePerPuzzleSeconds, bonusPoints })` -- time and bonus are per tournament, no global config form). `connections-admin-page.js` renders the whole "Connections" section into `#connections-admin-root` from a template string (paste one or many puzzles, or upload a .txt in the same format; Download exports the same format; inline Edit per row); its Daily and Classic tables use `admin-table-grouping.js` above, same as every other game's. Starter content lives in `docs/connections-content/` (daily/classic/tournament .txt, importable as-is).
- **`admin-page.js`** — page glue for `src/html/admin.html`. Content is organized into seven collapsible top-level sections: **Daily Activity Summary** (open by default, first section on the page -- a date picker (`wireActivitySummary()`, defaults to today) driving `activity-summary-data.js#getDailyActivitySummary()`, rendered as 4 stat cards (Logged Users/Guest/Registered/Total Plays, reusing the home page's `.status-stats-grid`/`.status-stat-card` classes from `components.css` as-is) plus a table grouped by game (Wordle/Sudoku/Word Search) with a per-game subtotal row and indented per-mode sub-rows, each showing Guest/Registered/Total counts), **Manual Executions** (renamed from "Championships" and moved to be the 2nd top-level section, right after Daily Activity Summary -- moved here specifically to remove the timezone-race problem the old visitor-triggered design had, see `progression/CLAUDE.md`'s `championship-service.js` entry for the full rationale. "Finalize Periods" -- a status table, one row per game × {Daily, Weekly, Monthly} (`renderChampionshipStatusTable()`), each showing either an already-finalized result (winner + points), a live countdown to its safe-to-finalize instant (`wireCountdowns()`, ticking every second off `progression/championship-service.js#periodSafeInstant()`, computed once per row at render time and stashed in a `data-countdown` attribute -- the countdown re-renders the whole table the moment any row crosses zero rather than tracking per-row transitions individually), or a "Finalize" button once safe (disabled otherwise) -- plus a page-wide "Run All Eligible" button (`finalizeAllPending()`). Grouped into a collapsible per calendar year, each containing a nested collapsible per month within it (`groupWordsByMonth()` keyed by the date's "YYYY-MM" prefix, further grouped by `groupMonthsByYear()` keyed by the "YYYY" prefix -- both reuse the page's existing `.admin-subsection`/`.card` collapsible markup, the month level just adding an `.admin-subsection-nested` modifier class for a lighter header background; wired locally within `#daily-words-table` rather than via the page-wide `wireCollapsibleSections()`, since these subsections are re-generated on every render and wiring them globally would double-bind the static sections elsewhere on the page -- the existing `closest('[data-collapsible]')`-based toggle logic needed no changes to support the nesting, since it already finds whichever subsection directly encloses the clicked header) so a pool spanning months or years doesn't become one long flat scroll; the year and month containing today both open by default, or the earliest seeded ones if today falls outside the seeded range (e.g. pre-launch). Word Search's admin tables reuse Sudoku's generic `.sudoku-daily-row`/`.sudoku-puzzle-form` CSS classes as-is rather than cloning parallel `.wordsearch-*` versions — already game-agnostic layout, same reuse precedent as `.tournament-row`/`.status-pill` being shared across all three games' admin tables. This grouping exists purely to keep the page scannable; it has no bearing on the data model.
  - `sudokuTournamentSettings`/`wordsearchTournamentSettings` are still entries in the one `CONFIG_FORMS` array (same shape as every other config form) but are deliberately rendered into their own game section instead of the General section's `#config-forms` list -- since each is a *global* setting (applies to every tournament of that game) sitting right above that game's own Tournaments table, admins were more likely to look for it there than in a general platform-config list unrelated to any specific game. `renderConfigForms(containerId, formIds)` takes a container id and a subset of `CONFIG_FORMS`' ids so it can be called three times (`init()`) — once for the General section's remaining forms, once each for `sudoku-tournament-settings-form` and `wordsearch-tournament-settings-form` inside their respective game sections — sharing one save-button wiring path (`CONFIG_FORMS.find()` by id still works regardless of which subset rendered the button, since ids are globally unique).
  - `renderConfigForms()`'s generic form renderer wraps each field in a `.config-form-field` div with its own `<label>` (built from each `CONFIG_FORMS` entry's `field.label`) — this only became visually necessary once `sudokuTournamentSettings` introduced the first 4-field config form; every earlier form had exactly one field, where the form's own title/description already made a separate label redundant.
  - Field `type` supports `'text'`/`'number'`/`'textarea'`/`'checkbox'` (the native `<input>` types, plus `'checkbox'` as a fourth explicitly-handled case since a checkbox's value lives in `.checked`, not `.value` — `cookieConsent`'s `enabled` field was the first user of `'checkbox'`; `wordValidationAPI`'s own `enabled` field, next to its `endpoint` text field, is the second). A checkbox field's value resolution falls back to `CONFIG_DEFAULTS[form.id][field.key]` when the field is `undefined` on the loaded doc (`data[field.key] !== undefined ? data[field.key] : CONFIG_DEFAULTS[form.id]?.[field.key]`) -- without this, a config doc saved *before* a given checkbox field existed renders it unchecked even though the actual runtime default is on, misleadingly suggesting it's off (and risking a silent flip to actually-off if the admin then hits Save without noticing). `admin.css`'s generic `.config-form-row input` styling (full-width, padded, bordered, meant for text/number/textarea) is explicitly overridden for `input[type="checkbox"]` -- reset padding/border/background, `align-self: flex-start` to opt out of the column's stretch, explicit 22×22px size with `accent-color` -- since without that override a checkbox inherited that box model and rendered tiny and oddly offset instead of a normal-sized toggle flush left under its label.
  - `stripCsvHeaderRow(lines)` is shared by all three games' import parsers (`parseWordListFile()`, `parseSudokuPuzzleListFile()`, `parseWordsearchDailyListFile()`) -- drops a leading `no,date,...` line before parsing, so a CSV downloaded from one of the "Download CSV" buttons can be re-uploaded through "Import" unchanged instead of the header row itself getting misread as a malformed data row.

The collapsibles are plain `<div data-collapsible>` + `<button>` (see `wireCollapsibleSections()`), **not** `<details>`/`<summary>` — `<details>` was tried first but its box width behaved inconsistently between open/closed states across at least one browser, which a `<details>`-based fix couldn't reliably override. The current approach toggles an `.open` class via a click handler, and CSS shows/hides the inner content with plain `display: none`/`block`, which can never affect the outer box's own width (already fixed at `width: 100%; max-width: var(--content-max-width)`).

## Ad slots

`config/ads` holds per-slot settings for all 9 ad placements across the site (`src/js/utils/ads.js#AD_SLOTS` is the canonical list — id, label, and a `group` used only to sort slots into the admin panel's sections above). Each slot has `enabled` (hide it entirely when off), `type` (`'google'` shows the existing static AdSense-placeholder markup already in the HTML — there's still no real AdSense integration, just an honest placeholder — while `'image'` rewrites the slot into a clickable image ad using `imageUrl`/`linkUrl`), and those two URL fields. `admin-page.js#renderAdSlotForms()` renders each group into its own container (`ad-slot-forms-home`/`-wordle`/`-sudoku`/`-wordsearch`) but all four share one in-memory `slots` object — saving any single slot's form re-reads/merges that shared map before writing the whole `config/ads` doc back, so editing e.g. a Wordle ad from the "Game wise" subsection never clobbers the Home ads. The actual per-page rendering happens automatically on every page load via `applyAdSlots()`, called from `src/js/app.js#loadHeaderFooter()` — admin-page.js only edits the settings, it doesn't render the ads itself.

## Bootstrapping the first admin

No code path can safely auto-grant admin — see the root `README.md` for the one-time manual step (sign up normally, then flip `isAdmin: true` on that account's `registeredUsers` doc via the Firebase console).

## Not implemented

There's no analytics panel and no pre-computed/scheduled jobs (no Cloud Functions in this app at all).

## Word validation

`config/wordValidationAPI.endpoint` (editable here, defaults to the Free Dictionary API's `v2` endpoint — **not** `v1`, which returns `502` instead of `404` for a nonexistent word, making "not a real word" indistinguishable from "the API is down") backs `src/js/games/wordle/wordle-word-validation.js#isRealWord()`, used both to reject non-dictionary words when creating a Challenge a Friend and live during play across all three Wordle modes (every guess that isn't the exact target word gets checked before it's accepted). It fails *open* — any non-404 response, a 5s timeout, or a network error all let the word/guess through rather than blocking play or challenge creation on a flaky third party. `config/wordValidationAPI.enabled` (a checkbox next to the endpoint field) is a full on/off switch, not just a "treat failures as valid" knob — when explicitly `false`, `isRealWord()` returns `true` immediately without ever calling the API at all, so an admin can turn the whole check off (e.g. the API's down, or they just don't want it) without a flood of "unreachable" warnings. Not wired into Daily Words or Tournament word entry in this section — an admin can still seed a nonsense "word" there without complaint.
