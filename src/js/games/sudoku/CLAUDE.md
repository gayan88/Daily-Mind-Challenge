# src/js/games/sudoku

`sudoku.html` has three modes, selected by a tab row: **Daily Challenge**, **Classic Sudoku**, and
**Tournament**. All three are live.

## Files

- **`sudoku-engine.js`** — the playable grid itself, mode-agnostic: `playSudokuRound({ container, puzzle, solution, timeLimitSeconds, maxErrors, onComplete })`. Tap-a-cell-then-tap-a-number entry (mobile-friendly, avoids raw `<input>` zoom/keyboard issues) -- or, once a cell is selected, type a digit 1-9 on a physical keyboard instead (Backspace/Delete clears it), same effect as the on-screen palette/Clear button. `selectCell()` explicitly calls `.focus()` on the chosen cell (a real `<button>`), since Safari in particular doesn't focus a button on a plain mouse click by default, which the keydown listener depends on (it's attached to `container`, and relies on focus being inside it for the event to bubble up). That container-scoped attachment (rather than `document`, which is what `wordle-engine.js`'s physical-keyboard listener has to use) is deliberate: `container` gets fully detached when a mode-tab switch replaces its parent's innerHTML, and a detached node never receives real keydown events again, so this listener can never leak into a later round the way Wordle's document-level one could before that was fixed -- removing it in `cleanup()` is just tidiness here, not a correctness requirement. Correctness is checked by direct string comparison against the known `solution` — there's no general constraint-solving/validation engine. Always shows a live stats bar (time + errors) — all three Sudoku modes display this per spec. `timeLimitSeconds`/`maxErrors` are optional (Tournament only): when set, the stats bar counts down instead of up, and hitting either limit ends the round as a loss (`timedOut: true` on a timeout), with the countdown starting immediately since it's a real time-attack constraint. Without `timeLimitSeconds` (Daily/Classic), the stats bar is a pure stopwatch that doesn't start ticking until the player's first cell selection (`selectCell()` calls a `startTimer()` guarded to only ever start the interval once) — otherwise page-load/read time before their first move would silently eat into the speed bonus. On a loss the solution is revealed in every non-given cell, with mismatched cells marked `.revealed`. Calls `onComplete({ won, errors, timeTakenSeconds, timedOut })` exactly once. Returns `{ destroy }` to stop its internal timer and remove the keydown listener — callers that might replace the container mid-round (e.g. a mode-tab switch) must call this, or the interval keeps ticking against a detached DOM element forever.
- **`sudoku-page.js`** — page glue for `sudoku.html`: `initShell()`, blocks admins from playing, then wires the three mode tabs (`wireModeTabs`), which owns one `activeRound` handle (via `setActiveRound`) so switching tabs mid-round always calls the previous round's `destroy()` first. `wireModeTabs()`'s initial mode reads `?tab=tournament` off the URL (opens straight into the Tournament tab -- the same deep-link mechanism as Wordle's `?tab=tournaments`, just singular since that's `sudoku.html`'s actual `data-mode` value) via the shared `TOURNAMENTS_TAB_URL` constant, which the Tournament completion share text also links to. **Daily Challenge** (`renderDailyMode`) gates on `checkPlayedToday(uid, 'sudoku')`, resolves today's puzzle via `sudoku-daily-data.js#getTodayChallenge()`, mounts the engine with no time/error limit, and on completion calls `recordDailyResult()` then shows `sudoku-summary-modal.js`. **Classic Sudoku** (`renderClassicMode` / `renderDifficultyPicker` / `playClassicRound`) has no played-today gate — pick Easy/Medium/Hard, get a random puzzle from that difficulty's pool via `sudoku-classic-data.js#getRandomClassicPuzzle()`, and the summary modal's "Close" returns to the difficulty picker so replaying is a one-click loop. **Tournament** (`renderTournamentMode` / `playSudokuTournamentRound` / `finishSudokuTournament`) lists active tournaments with each one's Start/Continue/Completed status, plays the player's current puzzle under the global `config/sudokuTournamentSettings` time limit and max errors, and — unlike Wordle Tournament — a failed puzzle does **not** reset progress: it banks 10 points immediately and the player moves straight to the next puzzle with a fresh timer/error count (a short inline pass/fail message, not the summary modal, appears between puzzles). Once every puzzle has been attempted, `finishSudokuTournament()` awards the one-time completion bonus and shows the summary modal for the whole run, with one breakdown line per puzzle built from `result.puzzleResults` -- shows each puzzle's time and error count (e.g. "Puzzle 2: 3:45 • 2 errors") rather than "Passed"/"Failed", since passing is the norm and the time/errors are the more informative thing to show; a puzzle's `points` (50 vs 10) still reflects whether it was actually passed, and passed puzzles get a checkmark icon as the pass/fail signal instead of the wording -- mirrors Wordle Tournament's per-word breakdown in structure, not wording. All three modes' modal calls pass `celebrate: true` (Sudoku has no separate "loss" screen outside Tournament's own inline per-puzzle fail message, so reaching this modal at all means a completion) plus `shareText`/`communityUrl`/`onShareCommunity`/`onShareFriends` for the two independent share bonuses (see Points below).
- **`sudoku-daily-data.js`** — Firestore layer for Daily Challenge: `getTodayChallenge()` (resolves today's puzzle via a direct date lookup, not a formula -- each `sudokuDailyPuzzles` doc is keyed by the exact "YYYY-MM-DD" date it plays on, set once when it's added by `src/js/admin/sudoku-admin.js#addDailySudokuPuzzle()`, so adding more puzzles later never recomputes or shifts which date any existing puzzle lands on -- same scheme as `wordle-daily-data.js#getTodayChallenge()`, see its own doc comment for the full rationale, including the pre-launch "always Challenge #1" fallback), `recordDailyResult()` (writes the points formula below to `gameScores` with the pre-existing `{uid}_sudoku_{date}` deterministic ID — unchanged from this app's original single-mode Sudoku, so `checkPlayedTodayAll()`'s hardcoded `{wordle, sudoku, wordsearch}` shape and the home page's "completed today" tile badge needed zero changes for this revamp). Also exports `timeBonus()`/`errorBonus()`, the two shared bonus-tier helpers Classic Sudoku reuses rather than duplicating (they're defined identically for both modes per spec).
- **`sudoku-classic-data.js`** — Firestore layer for Classic Sudoku: `getRandomClassicPuzzle(difficulty)` (queries `sudokuClassicPuzzles` by `difficulty`, picks one client-side — no "today's puzzle" concept here), `recordClassicResult()` (completion points by difficulty — `{easy:10, medium:15, hard:25}` — plus the same time/error bonuses as Daily). Classic allows unlimited scored replays per day, which the Daily doc-ID scheme can't support, so each round gets its own client-generated unique `gameScores` doc ID (`doc(collection(db,'gameScores')).id`, repurposing the `gameDate` field as an arbitrary unique token rather than a calendar date) — same pattern as `wordle-challenge`/`wordle-tournament`.
- **`sudoku-tournament-data.js`** — Firestore layer for Tournament: `listActiveSudokuTournaments()`, `getAttempt()` / `getOrStartAttempt()` (one progress doc per player per tournament, id `{tournamentId}_{uid}`, created at puzzle 1 on first play, with `puzzleResults: []` — resuming an unfinished attempt is just fetching this same doc), `recordPuzzleResult(tournament, uid, profile, { puzzleIndex, passed, errors, timeTakenSeconds })` (banks 50/10 points **and** advances `currentPuzzleIndex`/`puzzlesPassed`/`puzzlesFailed`/`puzzleResults` (appends `{ passed, errors, timeTakenSeconds }`, not just the boolean -- feeds the completion breakdown's/share text's per-puzzle time+error display) in a single `runTransaction`, so a browser closing mid-write can never lose a puzzle's points or leave the attempt doc out of sync with what was actually scored — stronger atomicity than Wordle Tournament needs, because a Sudoku puzzle failure doesn't reset progress the way a Wordle word failure does. Also idempotent against a client-level retry: if `currentPuzzleIndex` has already moved past the puzzle being recorded, it's a no-op read rather than a double-score), `completeTournamentIfNeeded(uid, profile, tournament, settings)` (one-shot completion bonus, wrapped in the same kind of single transaction as the bonus write + `completed`/`bonusAwarded` flags together — safely re-callable any time an attempt is revisited with `bonusAwarded` still false, e.g. after a dropped connection right after the last puzzle), and `markSharedToFacebook()`/`markSharedWithFriends()` (see Points below) -- both apply to the one-time completion-bonus doc rather than a single combined tournament-total doc, since a Sudoku Tournament run's score is split across many per-puzzle `gameScores` docs plus that bonus doc; `sudoku-page.js#finishSudokuTournament()` tracks the true running total itself in a closure variable rather than trusting either share function's own returned `newScore`.
- **`sudoku-summary-modal.js`** — shared post-round popup for all three modes: points breakdown (with optional per-line icons) and, once per run, for Tournament's final summary. A `celebrate` flag shows a trophy-in-a-circle + confetti header above the title -- all three Sudoku modes pass this, since (unlike Wordle) there's no separate "loss" screen this modal is ever used for. No colored-guess-grid visualization (unlike Wordle's summary modal) since Sudoku has no per-guess history to render. Tournament's per-puzzle pass/fail doesn't use this modal — see `sudoku-page.js` above. All three modes also pass `shareText`/`communityUrl`/`onShareCommunity`/`onShareFriends`, rendering the same two independent share options (+20 community, +10 friends — see Points below) as `wordle-summary-modal.js`, byte-for-byte the same markup/behavior minus the grid.
- **`sudoku-puzzles.js`** — the original static bank of 30 `{ puzzle, solution }` pairs, kept in place but no longer referenced by any live code. Left as a ready-made source an admin can copy-paste from when seeding `sudokuDailyPuzzles`/`sudokuClassicPuzzles` via the admin panel.

## Firestore schema

- **`sudokuDailyPuzzles/{id}`** (`id` = "1", "2", ...) + **`sudokuDailyPuzzles/_meta`** (`{ totalCount }`) — admin-managed, append-only (see `src/js/admin/sudoku-admin.js`).
- **`sudokuClassicPuzzles/{id}`** (one global numeric id sequence shared across all three difficulties) + `_meta` — `{ puzzle, solution, difficulty }`.
- **`sudokuTournaments/{autoId}`** — `{ name, puzzles: [{ puzzle, solution }, ...], completionBonus, active, createdAt }`. `completionBonus` is set per tournament at creation time (like Wordle Tournament's `bonusPoints`). Time limit and max errors per puzzle stay global, via `config/sudokuTournamentSettings` (edited through the generic admin config form). A tournament's own `puzzles.length` is what actually drives its completion check, not the global `puzzleCount` field on that same config doc — that field is just a guardrail admins see at creation time, so changing it later never breaks an already-created tournament's progress logic.
- **`sudokuTournamentAttempts/{tournamentId}_{uid}`** — `{ uid, displayName, tournamentId, currentPuzzleIndex, puzzlesPassed, puzzlesFailed, puzzleResults, startedAt, completed, completedAt, bonusAwarded }`. Exactly one attempt per player per tournament, ever — `completed` only ever flips false→true (enforced by `firestore.rules`), and none of the three counters ever reset, unlike `wordleTournamentAttempts`'s word-index reset on a loss. `puzzleResults` is a parallel array of `{ passed, errors, timeTakenSeconds }` (one entry per puzzle attempted, in order) feeding the completion modal's/share text's per-puzzle breakdown -- the counters alone can't reconstruct which specific puzzles passed vs. failed, or each one's time/errors.

## Points

- **Daily Challenge**: `25` (completing) `+ timeBonus(timeTakenSeconds)` `+ errorBonus(errors)` `+ 20` **and/or** `+10` (either outcome, two independent one-time bonuses, both claimable -- see Sharing below). `timeBonus`: `<600s:25 / <1200s:15 / else:10`. `errorBonus`: `≤3:50 / ≤6:40 / ≤9:30 / ≤12:20 / else:10`. Max pre-share: 100.
- **Classic Sudoku**: `{easy:10, medium:15, hard:25}` (completing) `+ timeBonus + errorBonus` `+ 20`/`+10` (share, see below). Same bonus tiers as Daily. Max pre-share: 100 (hard).
- **Tournament**: per puzzle, banked immediately — `50` if passed, `10` if failed (timeout or exceeding `maxErrors`). Plus a one-time `tournament.completionBonus` (set per tournament by the admin at creation, default suggestion 250) once every puzzle in the tournament has been attempted, regardless of individual pass/fail. Plus `+20`/`+10` for sharing (see below), applied to the completion-bonus doc.
- **Sharing** (all three modes alike): `+20` for "Copy Result & Share with Community" (`markSharedToFacebook()`) and `+10` for "Share with Friends" (`markSharedWithFriends()`) — two independent, one-time, **stackable** bonuses, not alternatives; a player can claim both. Daily and Classic use the generic `utils/points.js#markSharedToFacebook()`/`markSharedWithFriends()` (by `gameType`/`gameDate`, same functions Word Search's Daily/Classic use too) since each has one single `gameScores` doc holding its true total; Tournament uses its own per-mode copies in `sudoku-tournament-data.js` targeting the completion-bonus doc instead (see that file's entry above for why). `firestore.rules`' `isCommunityShareUpdate()`/`isFriendsShareUpdate()` independently bound each field's own delta across every gameType listed above.

Both Daily and Classic only score on actual completion — there's no "gave up" state, since Sudoku has no inherent turn limit outside Tournament mode.

All three modes share the app's "v1-pragmatic, not fully cheat-proof" points philosophy: outcomes are self-reported by the client, and `firestore.rules` bounds *how much* a write can award (deterministic create-only doc IDs, per-gameType score caps via `maxCreateScore()`) rather than verifying gameplay actually happened server-side.
